What is wrong

A SQL statement is assembled with template-literal interpolation or string concatenation and then executed. Interpolated values are spliced into the SQL text instead of being sent as bound parameters.

Evidence

supabase/functions/search-tasks/index.ts:23
21      SELECT id, title, description, status22      FROM public.tasks23      WHERE title ILIKE '%${searchTerm}%'24      ORDER BY created_at DESC25      LIMIT 25

Why it matters

An attacker can break out of the string literal and append their own SQL (e.g. ' UNION SELECT ... --) to read or modify any data the database role can reach, bypass filters, or cause denial of service.

How to fix it

Use parameterised queries / the driver's tagged-template API so values are always sent separately from SQL. Never pass user-built strings to raw/unsafe execution APIs. Escape LIKE wildcards if partial matching is needed, and validate input length/type.

Why it matters

Any unauthenticated user who can reach the endpoint can read or modify other users' data by supplying arbitrary identifiers; database Row Level Security is bypassed by the privileged credential.

How to fix it

Authenticate every request (verify the JWT from the Authorization header), then either query with a client scoped to the caller's token so RLS applies, or explicitly enforce ownership in the query. Reserve service-role keys for trusted back-office jobs.

import { createClient } from "npm:@supabase/supabase-js@2";

Deno.serve(async (req: Request) => {
  const authHeader = req.headers.get("Authorization");
  if (!authHeader) return Response.json({ error: "Unauthorized" }, { status: 401 });

  // Client scoped to the caller's JWT -> Row Level Security is enforced
  const supabase = createClient(
    Deno.env.get("SUPABASE_URL")!,
    Deno.env.get("SUPABASE_ANON_KEY")!,
    { global: { headers: { Authorization: authHeader } } },
  );

  const { data: { user }, error } = await supabase.auth.getUser();
  if (error || !user) return Response.json({ error: "Unauthorized" }, { status: 401 });

  // ...queries now run as `user` and are filtered by RLS policies
});

Validation notes
