## 5. Attack Chains

How individual weaknesses combine into higher-impact attack paths:

- **Unauthenticated Edge Function Exploitation and SQL Injection** (CW-001, CW-005): An attacker targets the unauthenticated 'search-tasks' edge function (CW-005) which bypasses RLS entirely. By leveraging the unsafe string interpolation vulnerability in the search query parameter (CW-001), the attacker injects malicious SQL commands to exfiltrate or alter unauthorized data across the database.
- **Privileged Execution and Privilege Escalation via Profile Updates** (CW-002, CW-006): An unauthenticated attacker abuses an unprotected edge function endpoint (CW-002) to interact with the database using privileged credentials. Combined with the unrestricted column updates on the profiles table (CW-006), the attacker can elevate standard user roles to administrative privileges.
- **Unrestricted Task Read Access and Stored XSS** (CW-003, CW-007): Due to the over-permissive RLS read policy on the tasks table allowing global access (CW-007), any authenticated user can view all tasks and comments. An attacker then injects malicious scripts into task comments, which are subsequently rendered unsanitized via dangerouslySetInnerHTML (CW-003) to hijack sessions of other users viewing the comments.

## 7. Overall Assessment

**Risk rating: Critical** (weighted risk score 70).

The systemic root causes stem from inconsistent enforcement of boundary controls, where Deno edge functions utilize privileged database connections directly without validating caller authentication or session contexts. Additionally, database migrations implement overly permissive Row Level Security (RLS) policies (such as using USING true or missing ownership validations on parent relationships) that rely entirely on client-side constraints rather than robust server-side boundaries. Addressing these issues requires centralizing authentication checks in all edge functions, transitioning away from unsafe raw SQL string interpolation, and hardening PostgreSQL RLS policies to strictly validate user ownership across all hierarchical tables.

**Positive observations**

- Row Level Security (RLS) is enabled on all primary database tables in the initial schema migrations, establishing a baseline security architecture.
- Database schema appropriately utilizes foreign key constraints to link profiles, projects, tasks, and task comments to Supabase auth users.
