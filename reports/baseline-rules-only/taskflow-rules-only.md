#### CW-001: SQL injection via string-built query

| | |
|---|---|
| **Severity** | Critical |
| **Status / confidence** | Confirmed / High confidence |
| **Category** | SQL Injection |
| **CWE** | CWE-89 |
| **OWASP Top 10** | A03:2021 Injection |
| **Affected location(s)** | `supabase/functions/search-tasks/index.ts:23` |
| **Detection** | Rule engine (not AI-verified) - rule CW-JS-SQLI-001 |

**Description**

A SQL statement is assembled with template-literal interpolation or string concatenation and then executed. Interpolated values are spliced into the SQL text instead of being sent as bound parameters.

**Vulnerable code (evidence)**

`supabase/functions/search-tasks/index.ts:23`

```

    22 |       FROM public.tasks
>   23 |       WHERE title ILIKE '%${searchTerm}%'
    24 |       ORDER BY created_at DESC
    25 |       LIMIT 25
```

**Potential impact**

An attacker can break out of the string literal and append their own SQL (e.g. `' UNION SELECT ... --`) to read or modify any data the database role can reach, bypass filters, or cause denial of service.

**Recommended fix**

Use parameterised queries / the driver's tagged-template API so values are always sent separately from SQL. Never pass user-built strings to raw/unsafe execution APIs. Escape LIKE wildcards if partial matching is needed, and validate input length/type.

**Secure code example**

```typescript

const pattern = `%${term.replace(/[\\%_]/g, "\\$&")}%`;

  SELECT id, name
  FROM public.items
  WHERE name ILIKE ${pattern}
  LIMIT 25
`;
```

**Validation notes / assumptions**

User-controlled request input is present in this handler and the query is executed through a raw/unsafe API, so the interpolated value reaches the database unescaped.

#### CW-005: Privilege escalation: users can modify `role` on `profiles`

| | |
|---|---|
| **Severity** | High |
| **Status / confidence** | Confirmed / High confidence |
| **Category** | Database Access Control |
| **CWE** | CWE-269 |
| **OWASP Top 10** | A01:2021 Broken Access Control |
| **Affected location(s)** | `supabase/migrations/002_access_policies.sql:20` |
| **Detection** | Rule engine (not AI-verified) - rule CW-SQL-RLS-004 |

**Description**

An UPDATE policy allows users to edit their own row, and that row contains an authorisation column (e.g. `role`). RLS restricts which rows can be changed, not which columns.

**Vulnerable code (evidence)**

`supabase/migrations/002_access_policies.sql:20`

```
    18 | TO authenticated
    19 | USING (id = auth.uid())
>   20 | WITH CHECK (id = auth.uid());
    21 | 
    22 | CREATE POLICY "Users can view projects"
```

**Potential impact**

A regular user can promote themselves (e.g. `role = 'admin'`) with a single API call and gain administrative capabilities wherever the application trusts that column.

**Recommended fix**

Revoke UPDATE on the privileged column(s) from client roles and grant UPDATE only on user-editable columns, or enforce immutability with a BEFORE UPDATE trigger. Store roles in a separate table writable only by the service role.

**Secure code example**

```sql
-- Clients may edit only their own non-privileged fields
REVOKE UPDATE ON public.profiles FROM authenticated;
GRANT UPDATE (full_name, bio) ON public.profiles TO authenticated;

-- Defence in depth: block privileged-column changes from client sessions
CREATE OR REPLACE FUNCTION public.prevent_profiles_role_change()
RETURNS trigger
LANGUAGE plpgsql
SET search_path = ''
AS $$
BEGIN
  IF NEW.role IS DISTINCT FROM OLD.role
     AND current_user <> 'service_role' THEN
    RAISE EXCEPTION 'role cannot be changed by clients';
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER profiles_prevent_role_change
BEFORE UPDATE ON public.profiles
FOR EACH ROW EXECUTE FUNCTION public.prevent_profiles_role_change();
```

**Validation notes / assumptions**

Policy "Users can update own profile" lets a user update their own row in `profiles`, but RLS is row-level only: nothing prevents them from changing the privileged column(s) `role` (e.g. setting role = 'admin'). No column-level REVOKE/GRANT or trigger protecting these columns was found.

**References:** <https://supabase.com/docs/guides/database/postgres/row-level-security>, <https://cwe.mitre.org/data/definitions/284.html>, <https://cwe.mitre.org/data/definitions/269.html>

#### CW-006: Over-permissive RLS read policy on `tasks` (USING true)

| | |
|---|---|
| **Severity** | High |
| **Status / confidence** | Confirmed / High confidence |
| **Category** | Database Access Control |
| **CWE** | CWE-284 |
| **OWASP Top 10** | A01:2021 Broken Access Control |
| **Affected location(s)** | `supabase/migrations/002_access_policies.sql:38` |
| **Detection** | Rule engine (not AI-verified) - rule CW-SQL-RLS-001 |

**Description**

A Row Level Security SELECT policy uses `USING (true)`, which makes every row visible to every user in the granted role, regardless of who owns the data.

**Vulnerable code (evidence)**

`supabase/migrations/002_access_policies.sql:38`

```
    36 | FOR SELECT
    37 | TO authenticated
>   38 | USING (true);
    39 | 
    40 | CREATE POLICY "Users can create tasks"
```

**Potential impact**

Any authenticated user can query the table directly through the auto-generated API and read other users' records (horizontal privilege escalation / data exposure).

**Recommended fix**

Replace `true` with a predicate that ties rows to the caller (ownership or project/team membership via auth.uid()). If some data must be public, expose it through a view containing only the non-sensitive columns.

**Secure code example**

```sql
DROP POLICY IF EXISTS "Users can view tasks" ON public.tasks;
CREATE POLICY "Users can view tasks (scoped)"
ON public.tasks
FOR SELECT
TO authenticated
USING (
  owner_id = (SELECT auth.uid())
  OR EXISTS (
    SELECT 1 FROM public.projects parent
    WHERE parent.id = tasks.project_id
      AND parent.owner_id = (SELECT auth.uid())
  )
);
```

**Validation notes / assumptions**

Policy "Users can view tasks" lets every signed-in user read every row of `tasks` (USING (true)). The table records ownership in `owner_id`, but the policy ignores it, so users can read records that belong to other users. This is inconsistent with the parent table `projects`, whose SELECT policy is restricted to the owner: rows of `tasks` leak data about projects the user cannot otherwise see.

     3 | 
>    4 | Deno.serve(async (request: Request) => {
     5 |   if (request.method !== "GET") {
     6 |     return Response.json(
```

**Potential impact**

**Recommended fix**

  const supabase = createClient(
    Deno.env.get("SUPABASE_URL")!,

  );

  const { data: { user }, error } = await supabase.auth.getUser();
  if (error || !user) return Response.json({ error: "Unauthorized" }, { status: 401 });

  // ...queries now run as `user` and are filtered by RLS policies
});
```

A direct database connection (typically a privileged role that is not subject to RLS) is used in a public request handler and no authentication check was found.
